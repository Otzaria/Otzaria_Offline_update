# הורדות עם המשך אוטומטי

חבילת Dart משותפת למתקין אוצריא, לעדכון הלאנצ׳ר, לחנות התוספים
ולתוכנות הנוספות. מנגנון הורדת הספרייה הוא של `seforim_library_updater`.

`windows_elevation.dart` מרכז את הרמת ההרשאות בווינדוס עבור `otzaria_manager`
ו-`custom_apps_manager`: בדיקת ה-token, פונקציית ציטוט ארגומנטים אחת
(`WindowsElevation.quoteArgument`), הפעלה לא-מורמת ב-`CreateProcessWithTokenW`
והרצה מורמת ב-`ShellExecuteExW` (`ElevatedProcess`).

ההורדה נכתבת ל־`<destination>.part`, והזהות שלה ל־`<destination>.resume`.
רק קובץ שהורד בשלמותו מחליף את היעד. בכשל נשמרים בייטים רק כשיש
`ETag` חזק וגודל כולל ידוע; ההמשך שולח `Range` יחד עם `If-Range`.
שינוי בכתובת או בגודל המוצהר פוסל את החלקי. תשובת `200` לבקשת המשך
מתחילה מאפס, ותשובת `416` מאפשרת בקשה מלאה אחת בלבד.

בניתוק או בתקיעה נעשה ניסיון המשך אוטומטי אחד, אם נשמר חלקי שניתן
לחדש. אם גם הוא נכשל, לחיצה נוספת על הורדה ממשיכה את העבודה, גם אחרי
פתיחה מחדש. בלי תמיכת שרת בהמשך, הניסיון הבא מתחיל את הקובץ מאפס.
ביטול יזום אינו מפעיל ניסיון נוסף. אין בחבילה דיאלוגים או הגדרות משתמש.

`keepPartialOnCancel: true` שומר גם בביטול את ההתקדמות שניתן לחדש.
המתקינים והתוספים משתמשים בו כדי לאפשר סגירה והמשך; ביטול מפורש בכלי
מחזיר בנפרד את מצב המראה הקודם. ברירת המחדל בחבילה נשארת שחזור החלקי
שהיה לפני הניסיון, או מחיקתו אם ההורדה התחילה בניסיון הזה.

זמן קצוב חל על החיבור ועל חוסר התקדמות ברשת, והבקשה מבוטלת בסיום
כל ניסיון. הכתיבה מפעילה לחץ נגדי כל 4MB כדי לא לצבור הורדה שלמה
בזיכרון כשהכונן איטי. חישוב SHA-256 אופציונלי מתבצע בזרימה; בעת
המשך נקרא תחילה החלק שכבר נשמר.

בקשות ל־GitHub API עוברות כולן דרך `githubGet`: אותן כותרות
(`User-Agent`, גרסת ה־API), אותו זמן קצוב, ופענוח UTF-8. תשובת 403/429
עם `Retry-After` או `X-RateLimit-Remaining: 0` הופכת ל־`GithubRateLimitException`
עם זמן האיפוס (מחושב מול שעון השרת, עד שעה לכל היותר), ועד אז בקשות
נוספות ל־`api.github.com` נכשלות מיד בלי לפנות לרשת. הורדות הקבצים
עצמן ו־raw אינן חסומות. כל לקוח שומר על הפענוח ועל הודעות השגיאה שלו.

הבדיקות מכסות חידוש, החלפת נכס, התעלמות מטווח, תגובות פגומות,
תקיעה, ביטול ואימות גודל, כולל ניתוק מול שרת HTTP מקומי אמיתי.
לא נבדקה הורדה משרתי הייצור או מסע הורדה על כונן USB.

## מדידות מול מסייע ההורדה של אוצריא (#149)

הדיווח "איטי יותר ממסייע ההורדה" **לא שוחזר, והסיבה לא הוכחה.** הכלים
ב־`tool/download_bench/` (חבילה עצמאית בשורש). הקצבים ב־MiB/s, כלומר
חלוקה ב־1,048,576. הסביבה: Windows 11, Dart 3.13.2, `curl 8.22.0` עם
Schannel, מנוע `809ce54`. זמן ה־hash והאימות נמדד בנפרד ואינו נכלל בקצב.

**שרת מקומי** (`local_suite.sh range 4194304`, תקרה של 4 MiB/s **לכל חיבור**,
קובץ של 256 MiB):

| מסלול | MiB/s |
|---|---|
| curl, חיבור אחד / ארבעה טווחים | 4.00 / 15.77 |
| `PatchDownloader`, 1 / 2 / 4 חיבורים | 3.99 / 7.63 / 14.51 |
| `downloadFile` (מתקינים, לא מתפצל) | 3.99 |

עם `norange` כל המסלולים חוזרים לחיבור אחד, כ־4.0.

**GitHub מאחורי NetFree** (`github_suite.sh`, 2026-10-30, נכס של 102 MiB,
הבדיקה המקדימה קיבלה `206`):

| מסלול | MiB/s |
|---|---|
| curl, חיבור אחד / ארבעה טווחים | 3.45 / 3.40 |
| `PatchDownloader`, 2 / 4 חיבורים | 3.34 / 3.37 |
| `downloadFile` | 2.94 |

**מה אפשר להסיק.** השרת המקומי מדגים מנגנון אפשרי אחד: כשכל חיבור מוגבל
בנפרד, curl עם ארבעה טווחים מקדים את שני החיבורים שלנו לקובץ (ואת החיבור
היחיד של מתקין). המדידה לא שוללת גורמים אחרים, ואין ראיה שהרשת של המדווח
מתנהגת כך. ב־GitHub הקצבים הדומים בכל המסלולים מתיישבים עם תקרה משותפת
לקו, אבל לבדם אינם מוכיחים מה מגביל אותו.

**מה נבדק ובאיזו רמה.** מסייע ה־**Windows** (Inno Setup) נקרא מהקוד ב־
`Otzaria/otzaria@71d1a57`: curl קודם, ארבעה טווחים בקבצים מ־64MB אחרי
שהבדיקה המקדימה קיבלה `206`, וקובץ אחד בכל פעם. `curl_bench.sh` **מחקה**
את ההתנהגות הזו ואינו המסייע עצמו. לא הורצו: המסייע הבנוי, המסייעים של
macOS ו־Linux, והכלי שלנו עם הממשק, ה־hash ויעד USB.
